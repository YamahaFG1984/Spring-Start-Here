架构风格与 XML 配置

两个书里放在附录、但工作中迟早会遇到的话题：你写的 Spring 应用在整个系统里处在什么位置，以及老项目里那些 <bean> 标签是怎么回事。

B.1 四种架构风格

本书每个示例都是一个独立的小应用。真实系统由多少个这样的应用组成、它们之间怎么分工，就是架构风格要回答的问题。书的附录 A 按演进顺序讲了下面几种。

风格一句话好处代价
单体
Monolith		所有功能在一个应用里，一起打包、一起部署开发、调试、部署都简单；方法调用就是普通 Java 调用；一个数据库事务能管住所有操作应用变大后，任何小改动都要整体发布；只能整体扩容；团队多了容易互相踩
面向服务
SOA		按业务能力拆成若干较大的服务，通过网络互相调用服务可以独立部署和扩容引入网络调用的全部问题；服务间常共享数据库或依赖一个中心化的总线，耦合仍然不低
微服务
Microservices		拆得更细，每个服务有自己的数据库，由一个小团队独立负责独立发布、独立扩容、技术栈可以不同；故障能被隔离分布式系统的复杂度：调用会失败会超时、没有跨服务事务、要有服务发现、链路追踪、统一配置
无服务器
Serverless		只写函数，由云平台在请求到来时拉起运行，按调用计费不用管服务器；没流量时不花钱冷启动延迟；被平台绑定；长时间运行和有状态的逻辑不适合
书里反复强调的一句话：不要因为流行就上微服务 微服务解决的是组织和规模的问题：几十个团队改同一个应用改不动了，或者某一块的流量是其他部分的一百倍。它不会让代码变简单，只会把复杂度从代码内部搬到网络上。一个团队、流量平平的系统，单体几乎总是更好的起点，等确实遇到单体的痛点再拆。

这和本书的章节有什么关系

章节在单体里在微服务里
第 2–6 章 容器与 AOP完全一样。每个服务内部都是一个 Spring 上下文
第 10 章 实现 REST主要给前端用也是服务之间互相调用的接口
第 11 章 消费 REST偶尔调第三方接口日常。ssh_ch11_ex1 调 ssh_ch11_payments 就是两个微服务的最小模型；OpenFeign 也正是 Spring Cloud 为这个场景准备的
第 13 章 事务@Transactional 能管住一个用例里的全部写操作只能管住一个服务自己的数据库。跨服务的一致性要靠补偿、消息、Saga 等模式，不在本书范围内
第 9 章 会话存在内存里就行多实例部署后必须外置（Spring Session + Redis），或改用无状态的令牌

B.2 用 XML 配置上下文

第 2–3 章讲了三种往上下文里加 bean 的方式，其实还有第四种，也是 Spring 最早的方式：XML。新项目已经不用它，但 2015 年以前启动的项目里大量存在，读得懂是必要的。书的附录 B 只用了两页，这里也只讲到“能读懂”为止。

src/main/resources/config.xml仓库里没有对应工程
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
           http://www.springframework.org/schema/beans/spring-beans.xsd">

    <bean id="parrot1" class="com.example.Parrot">
        <property name="name" value="Koko"/>          <!-- 调 setName("Koko") -->
    </bean>

    <bean id="parrot2" class="com.example.Parrot" primary="true">
        <property name="name" value="Miki"/>
    </bean>

    <bean id="person" class="com.example.Person">
        <property name="name" value="Ella"/>
        <property name="parrot" ref="parrot1"/>       <!-- 注入另一个 bean -->
    </bean>

</beans>
Main.java换一个上下文实现类，其余用法不变
var context = new ClassPathXmlApplicationContext("config.xml");
Person person = context.getBean(Person.class);

XML 和注解的对照

XML注解 / Java 配置章节
<bean id="x" class="…"/>@Bean 方法，或类上的 @Component2
<property name="p" value="…"/>在 @Bean 方法里调 setter2
<property name="p" ref="y"/>setter 注入，@Autowired3
<constructor-arg ref="y"/>构造器注入3
primary="true"@Primary2
scope="prototype"@Scope(BeanDefinition.SCOPE_PROTOTYPE)5
lazy-init="true"@Lazy5
<context:component-scan base-package="…"/>@ComponentScan2
<aop:aspectj-autoproxy/>@EnableAspectJAutoProxy6
new ClassPathXmlApplicationContext(…)new AnnotationConfigApplicationContext(…)2
概念一个都没变 对照表说明了一件事：bean、依赖注入、作用域、切面这些概念从 Spring 1.0 起就是现在这样，变的只是写法。XML 被淘汰的原因很实际：类名和属性名都是字符串，写错了要到启动时才发现，重命名类时 IDE 也帮不上忙；而 Java 配置是能编译检查的代码。
遇到老项目，按上表把 XML 逐行读成你熟悉的注解就行。两种方式还可以混用：在配置类上加 @ImportResource("classpath:config.xml")，就能把一份 XML 里的 bean 并入注解配置的上下文，迁移老项目时通常这样逐步替换。

自测

单体应用是不是就意味着代码乱、没有分层？

不是。单体说的是部署单元只有一个，和内部结构无关。本书第 4 章的 Service / Repository / Proxy 分层、面向接口编程，在单体里一样成立。一个模块边界清晰的单体，以后要拆也容易；一个没有边界的单体，拆成微服务只会得到一团互相调用的小服务。

把单体拆成两个服务后，原来一个 @Transactional 方法里的两次写操作会怎样？

如果两次写操作分到了两个服务、两个数据库里，它们就不再处于同一个数据库事务中。第一个服务提交之后第二个服务失败，第一个不会自动回滚。这是微服务最大的代价之一，也是为什么拆分边界要尽量让“必须同时成功”的数据留在同一个服务里。

XML 配置在 Spring 7 里还能用吗？

能。ClassPathXmlApplicationContext 和 @ImportResource 都还在，Spring 一直保持着对它的兼容。只是新功能的文档和示例都以注解和 Java 配置为准，Spring Boot 的自动配置也完全基于后者。
