第 15 章 · 第二部分 实现

单元测试

本章有个反直觉的重点：单元测试里没有 Spring。不启动上下文，不注入 bean，就是普通 Java 对象加 Mockito。之所以放在这本书里，是因为只有前面 14 章的“依赖注入”做对了，这一章才写得出来。

本章代码位置 第 2 版把测试拆成了两章，没有新建工程，测试类加在已有工程里：
ssh_ch14_ex1/src/test/java/.../TransferMoneyUnitTests.java 手工 mock
ssh_ch14_ex1/src/test/java/.../TransferServiceWithAnnotationsUnitTests.java 注解版
ssh_ch9_ex1/src/test/java/.../unit/LoginControllerUnitTests.java 控制器单测

15.1 什么是“单元”

为什么第 3 章要强调构造器注入 因为它让这一章成为可能。new TransferService(mockRepository) 一行就能装配好被测对象。
如果当初写的是字段注入（@Autowired private AccountRepository repo;），测试里就没有任何正常途径把 mock 塞进去，只能靠反射或者启动整个 Spring 上下文。可测试性是好设计的副产品，不是额外工作。

15.2 手工版：看清全部机制

ssh_ch14_ex1 · TransferMoneyUnitTests.java
public class TransferMoneyUnitTests {          // 注意：没有任何 Spring 注解

    private AccountRepository accountRepository;
    private TransferService transferService;

    @BeforeEach
    void setUp() {
        accountRepository = mock(AccountRepository.class);        // ① 造替身
        transferService = new TransferService(accountRepository); // ② 手工注入
    }

    @Test
    @DisplayName("""
            GIVEN a valid sender and receiver account
            WHEN transferMoney is called
            THEN the amounts are updated for both accounts
            """)
    public void transferMoneyHappyFlow() {
        Account sender = new Account();
        sender.setId(1L);
        sender.setAmount(new BigDecimal("1000"));

        Account receiver = new Account();
        receiver.setId(2L);
        receiver.setAmount(new BigDecimal("1000"));

        given(accountRepository.findById(1L)).willReturn(Optional.of(sender));    // ③ 编排
        given(accountRepository.findById(2L)).willReturn(Optional.of(receiver));

        transferService.transferMoney(1L, 2L, new BigDecimal("100"));             // ④ 执行

        verify(accountRepository).changeAmount(1L, new BigDecimal("900"));        // ⑤ 断言
        verify(accountRepository).changeAmount(2L, new BigDecimal("1100"));
    }
}

验证“没有发生”同样重要

失败路径的测试
@Test
@DisplayName("""
        GIVEN a non-existent sender account
        WHEN transferMoney is called
        THEN AccountNotFoundException is thrown
        """)
public void transferMoneySenderNotFound() {
    given(accountRepository.findById(1L)).willReturn(Optional.empty());

    assertThrows(AccountNotFoundException.class,
            () -> transferService.transferMoney(1L, 2L, new BigDecimal("100")));

    verify(accountRepository, never())                    // ← 关键：确认没有动过钱
            .changeAmount(anyLong(), any(BigDecimal.class));
}
never() 是这个测试的灵魂 只断言“抛了异常”是不够的——万一代码先扣了钱再抛异常呢？verify(..., never()) 明确验证了失败时账户余额一分钱都没动。写测试时多问一句“不该发生什么”，往往能发现真正的 bug。

15.3 注解版：Mockito 替你装配

ssh_ch14_ex1 · TransferServiceWithAnnotationsUnitTests.java
@ExtendWith(MockitoExtension.class)              // 启用 Mockito 的注解处理
public class TransferServiceWithAnnotationsUnitTests {

    @Mock
    private AccountRepository accountRepository;      // 自动创建替身

    @InjectMocks
    private TransferService transferService;          // 自动 new 并把上面的 mock 注进去

    // 不再需要 @BeforeEach —— 测试方法体和手工版完全一样
}
手工版
private AccountRepository accountRepository;
private TransferService transferService;

@BeforeEach
void setUp() {
  accountRepository =
      mock(AccountRepository.class);
  transferService =
      new TransferService(accountRepository);
}

机制全部可见，适合第一次学。

注解版
@ExtendWith(MockitoExtension.class)
class …Tests {

  @Mock
  private AccountRepository accountRepository;

  @InjectMocks
  private TransferService transferService;
}

依赖一多优势明显，日常首选。

两者完全等价。@InjectMocks 会按“构造器 → setter → 字段”的顺序尝试注入。注意：@InjectMocks 注入失败时不报错，只是留 null，然后你在测试里得到一个莫名其妙的 NPE。构造器注入的类不会有这个问题——这又是一条选择构造器注入的理由。

15.4 控制器也能纯单元测试

ssh_ch9_ex1 · unit/LoginControllerUnitTests.java
@ExtendWith(MockitoExtension.class)
public class LoginControllerUnitTests {

    @Mock private Model model;                    // 连 Spring 的 Model 都是 mock
    @Mock private LoginProcessor loginProcessor;
    @InjectMocks private LoginController loginController;

    @Test
    @DisplayName("""
        GIVEN  Valid credentials are provided
        WHEN   The loginPost method is called
        THEN   The user is redirected to the login page with a success message
        """)
    public void loginPostTestSuccess() {
        given(loginProcessor.login()).willReturn(true);

        String result = loginController.loginPost("natalie", "password", model);

        assertEquals("login.html", result);
        verify(model).addAttribute("message", "You are now logged in.");
    }
}
注意它测的是什么，不测什么 它直接调用 Java 方法，没有 HTTP，没有 Spring 上下文。所以它能验证：分支逻辑对不对、往 Model 里放了什么、返回了哪个视图名。
它验证不了：@PostMapping("/") 这个路由映射对不对、@RequestParam 绑定行不行、JSON 序列化是否正常。那些是第 16 章 MockMvc 的职责。

该测什么、不该测什么

适合单元测试不适合，交给集成测试（第 16 章）
业务规则、分支、边界条件路由映射、参数绑定
异常路径、"不该发生"的验证JSON 序列化/反序列化
计算逻辑（如金额加减）SQL 是否正确、事务是否回滚
与依赖的交互契约（调了什么、传了什么）Spring 配置和 bean 装配是否正确
getter/setter 不用测 书里明确说了：不要为了覆盖率去测没有逻辑的代码。测试的价值在于捕获会出错的东西，给 setName() 写测试只会增加维护负担。

与书中的差异

项书中（第 1 版第 15.2.1 节）仓库（第 2 版第 15 章）
章节结构单元测试和集成测试同在第 15 章拆成第 15、16 两章（对应 commit CH15/CH16）
工程随书示例工程不新建工程，测试类加到 ssh_ch14_ex1 和 ssh_ch9_ex1
Mockito API相同：mock()、@Mock、@InjectMocks、@ExtendWith(MockitoExtension.class)、given().willReturn()、verify()
@DisplayName短句用 Java 文本块写多行 GIVEN/WHEN/THEN
Mockito 的 API 非常稳定。唯一要留意的是它有两套等价语法：when(x).thenReturn(y)（Mockito 原生风格）和 given(x).willReturn(y)（BDD 风格）。仓库两种都用了——第 15 章的测试用 BDD 风格，第 16 章的一些测试用 when/thenReturn。功能完全一样，挑一种在团队里统一即可。

动手练习

动手 · 跑测试并让它失败

cd ssh_ch14_ex1
./mvnw test -Dtest=TransferMoneyUnitTests
./mvnw test -Dtest=TransferServiceWithAnnotationsUnitTests
  1. 把 TransferService.transferMoney 里的 subtract 改成 add，重跑测试——看它失败，并读懂失败信息。一个从不失败的测试等于没有测试。
  2. 把失败路径测试里的 verify(..., never()) 那两行注释掉，然后故意把 service 改成“先扣钱再检查 receiver 是否存在”。你会发现测试依然通过——这就是 never() 存在的意义。
  3. 给 transferMoney 加一条“转账金额必须大于 0”的规则，然后先写测试再写实现，体会一次 TDD。
  4. 对比 TransferMoneyUnitTests（手工）和 TransferServiceWithAnnotationsUnitTests（注解）：测试方法体一模一样，差别只在装配部分。

本章自测

为什么单元测试里完全不需要 Spring？

因为 Spring 的职责是“帮你把对象装配起来”。测试里对象由你手工装配（new TransferService(mock)），装配这件事就不需要框架了。好处非常实在：不启动上下文，一个测试从几秒变成几毫秒，几百个单元测试也能在一次保存后立刻跑完。

verify() 和 assertEquals() 什么时候各用哪个？

方法有返回值时，用 assertEquals 断言返回值；方法返回 void、效果体现在“调用了依赖”上时，用 verify 断言交互。transferMoney 返回 void，钱的变化是通过调用 repository.changeAmount() 实现的，所以只能用 verify。

mock 会不会让测试变得“测了个寂寞”？

这是个真实风险。如果 mock 的行为和真实实现对不上（比如你假设 findById 返回 Optional.of(...)，但真实实现在某些情况返回 empty），单元测试全绿而生产照崩。所以单元测试不能替代集成测试——第 16 章的 @SpringBootTest 用真实装配跑一遍，两者是互补关系，不是二选一。
