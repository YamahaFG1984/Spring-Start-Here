16.1 集成测试测的是什么

16.2 @SpringBootTest + @MockitoBean

ssh_ch14_ex1 · TransferServiceSpringIntegrationTests.java
@SpringBootTest                     // ← 启动完整的 Spring 上下文
public class TransferServiceSpringIntegrationTests {

    @MockitoBean                    // ← 用一个 mock 替换掉上下文里的这个 bean
    private AccountRepository accountRepository;

    @Autowired                      // ← 从上下文里拿真实的 service（依赖已被自动注入）
    private TransferService transferService;

    @Test
    public void transferMoneyHappyFlow() {
        Account sender = new Account();
        sender.setId(1L); sender.setAmount(new BigDecimal("1000"));
        Account receiver = new Account();
        receiver.setId(2L); receiver.setAmount(new BigDecimal("1000"));

        given(accountRepository.findById(1L)).willReturn(Optional.of(sender));
        given(accountRepository.findById(2L)).willReturn(Optional.of(receiver));

        transferService.transferMoney(1L, 2L, new BigDecimal("100"));

        verify(accountRepository).changeAmount(1L, new BigDecimal("900"));
        verify(accountRepository).changeAmount(2L, new BigDecimal("1100"));
    }
}
对比第 15 章：测试方法体一模一样 把这个类和 TransferServiceWithAnnotationsUnitTests 并排放——测试逻辑逐字相同，只有类顶部的三行不同：
第 15 章 · 单元
@ExtendWith(MockitoExtension.class)
@Mock       AccountRepository …
@InjectMocks TransferService …

Mockito 装配。不启动 Spring，毫秒级。

第 16 章 · 集成
@SpringBootTest
@MockitoBean AccountRepository …
@Autowired   TransferService …

Spring 装配。顺带验证了配置和 @Transactional。

仓库把这两个类都留着，就是为了让你做这个对比。

本章最重要的版本差异：@MockBean → @MockitoBean
书中（Boot 2.x）
import org.springframework.boot
  .test.mock.mockito.MockBean;

@MockBean
private AccountRepository repo;
仓库（Boot 4.x）
import org.springframework.test
  .context.bean.override.mockito
  .MockitoBean;

@MockitoBean
private AccountRepository repo;

为什么变：Spring Framework 6.2 把 bean 替换能力从 Spring Boot 提升到了框架核心（@MockitoBean、@MockitoSpyBean、@TestBean），非 Boot 项目也能用。@MockBean 在 Boot 3.4 被标记废弃，Boot 4 已彻底移除。
所以书里所有 @MockBean 在这个仓库都要写成 @MockitoBean——照抄书上的代码会直接编译失败。

16.3 MockMvc：从 HTTP 请求开始测

ssh_ch14_ex1 · TransferMoneyTests.java
@SpringBootTest
public class TransferMoneyTests {

    @Autowired private WebApplicationContext context;
    private MockMvc mockMvc;

    @MockitoBean private AccountRepository accountRepository;

    @BeforeEach
    void setup() {
        this.mockMvc = MockMvcBuilders.webAppContextSetup(context).build();
    }

    @Test
    void transferMoneySuccess() throws Exception {
        Account sender = new Account();  sender.setId(1);  sender.setAmount(new BigDecimal("1000"));
        Account receiver = new Account(); receiver.setId(2); receiver.setAmount(new BigDecimal("1000"));

        given(accountRepository.findById(1L)).willReturn(Optional.of(sender));
        given(accountRepository.findById(2L)).willReturn(Optional.of(receiver));

        mockMvc.perform(post("/transfer")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""
                        {
                            "senderAccountId": 1,
                            "receiverAccountId": 2,
                            "amount": 100
                        }
                        """))
                .andExpect(status().isOk());

        verify(accountRepository).changeAmount(1L, new BigDecimal("900"));
        verify(accountRepository).changeAmount(2L, new BigDecimal("1100"));
    }
}
MockMvc 到底跑了什么 它不启动 Tomcat、不开端口、不走网络，但会走完整的 Spring MVC 处理链：路由匹配 → 参数绑定 → JSON 反序列化 → 调用控制器 → 序列化响应 → 异常处理。
所以它能验证第 15 章的纯单元测试验证不了的那些东西：@PostMapping("/transfer") 这个路径对不对、@RequestBody 能不能正确把 JSON 变成 TransferRequest。而且它比启动真服务器快一个数量级。

两种构建方式

webAppContextSetup —— 更真实
@Autowired WebApplicationContext context;

mockMvc = MockMvcBuilders
    .webAppContextSetup(context)
    .build();

用真实上下文里的全部 MVC 配置：消息转换器、@RestControllerAdvice、拦截器、格式化器全都在。
仓库绝大多数测试用这个。

standaloneSetup —— 更轻
PurchaseController c =
    new PurchaseController(mockRepo);

mockMvc = MockMvcBuilders
    .standaloneSetup(c)
    .build();

只注册指定的控制器，用默认 MVC 配置。快，但测不到你的全局配置。
ssh_ch12_ex2 / ex3 用的是这种。

16.4 连数据库一起测

ssh_ch12_ex1 的测试是另一种风格：不 mock 任何东西，真往 H2 里写再读出来断言。

ssh_ch12_ex1 · PurchaseControllerTests.java
@SpringBootTest
class PurchaseControllerTests {

    @Autowired private PurchaseController purchaseController;
    @Autowired private PurchaseRepository purchaseRepository;   // 真实的，连着 H2

    @Test
    void storePurchaseTest() throws Exception {
        mockMvc.perform(post("/purchase")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                { "product": "T-Shirt", "price": 15.00 }
                                """))
                .andExpect(status().isOk());

        List<Purchase> purchases = purchaseRepository.findAllPurchases();   // 真查数据库
        assertFalse(purchases.isEmpty());
        assertEquals("T-Shirt", purchases.get(purchases.size() - 1).getProduct());
    }
}
这类测试要小心测试间的污染 上面的写法用 get(size() - 1) 取最后一条，就是因为前一个测试可能已经插了数据。更稳妥的做法是给测试类加 @Transactional——Spring 会在每个测试方法结束后自动回滚，数据库回到初始状态。

三种测试怎么选

单元测试（15 章）上下文集成测试MockMvc 端点测试
启动 Spring否是是
速度毫秒秒（上下文可缓存复用）秒
覆盖一个类的逻辑装配 + 事务 + AOP路由 + 绑定 + 序列化 + 异常处理
数量建议最多适量覆盖关键端点
上下文是会被缓存的 Spring Test 会按“配置指纹”缓存上下文：多个测试类只要配置相同，就复用同一个上下文，只在第一个测试时付出启动代价。所以尽量让测试类的配置保持一致——每加一处不同的 @MockitoBean 或 @TestPropertySource，就可能多启动一个上下文，整体测试时间成倍增长。

本章自测

@MockBean 改名成 @MockitoBean 只是换个名字吗？

不只是。它的归属变了：从 Spring Boot 的测试模块（org.springframework.boot.test.mock.mockito）挪到了 Spring Framework 的测试核心（org.springframework.test.context.bean.override.mockito）。这意味着不用 Spring Boot 的项目也能用它，而且它属于一套更通用的“bean 覆盖”机制，同族还有 @MockitoSpyBean（部分 mock）和 @TestBean（用自定义实现替换）。

MockMvc 和真启动服务器（webEnvironment = RANDOM_PORT）有什么区别？

MockMvc 在同一个 JVM 里模拟请求，不经过网络栈，快很多，但也测不到真实的 HTTP 层行为（真实的连接、压缩、Servlet 容器配置）。@SpringBootTest(webEnvironment = RANDOM_PORT) 会真的启动 Tomcat，配合 TestRestTemplate/RestClient 发真实请求——更真实但更慢。绝大多数场景 MockMvc 就够了；只有验证真实 HTTP 行为（比如 HTTPS、超时、自定义 Servlet Filter）时才需要真服务器。

集成测试写多少合适？

测试金字塔的经验比例大致是 70% 单元 / 20% 集成 / 10% 端到端。集成测试贵在启动上下文，写太多整个构建会慢到没人愿意跑。把它们用在“装配和配置容易出错”的地方：REST 端点的契约、事务是否真回滚、自定义配置是否生效。纯业务分支留给单元测试。
