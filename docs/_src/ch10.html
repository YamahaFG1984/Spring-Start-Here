实现 REST 服务

前三章的应用返回 HTML 给浏览器。这一章换一个受众：另一个程序。返回的不再是页面，而是 JSON。这是今天绝大多数 Spring 后端应用的形态。

本章工程 ssh_ch10_ex1 @ResponseBody · ex2 @RestController · ex3 返回对象/集合 · ex4 ResponseEntity 定制状态与头 · ex5 控制器内 try/catch · ex6 @RestControllerAdvice · ex7 @RequestBody · ssh_ch10_openapi （书中没有）OpenAPI 契约先行

10.1 从返回视图到返回数据

ssh_ch10_ex1 · 逐个方法标注
@Controller
public class HelloController {

  @GetMapping("/hello")
  @ResponseBody
  public String hello() { return "Hello!"; }

  @GetMapping("/ciao")
  @ResponseBody
  public String ciao() { return "Ciao!"; }
}
ssh_ch10_ex2 · 类级简写
@RestController
public class HelloController {

  @GetMapping("/hello")
  public String hello() { return "Hello!"; }

  @GetMapping("/ciao")
  public String ciao() { return "Ciao!"; }
}
@RestController = @Controller + @ResponseBody。就这么简单。实际项目中一律用 @RestController，ex1 只是为了让你看清它由什么组成。

10.2 返回对象与集合

ssh_ch10_ex3 · controllers/CountryController.java
@RestController
public class CountryController {

    @GetMapping("/france")
    public Country france() {
        return Country.of("France", 67);
    }

    @GetMapping("/all")
    public List<Country> countries() {
        return List.of(Country.of("France", 67), Country.of("Spain", 47));
    }
}
$ curl http://localhost:8080/france
{"name":"France","population":67}

$ curl http://localhost:8080/all
[{"name":"France","population":67},{"name":"Spain","population":47}]
Jackson 靠 getter 工作，不是靠字段 序列化出来的 JSON 属性名来自 getter 方法名（getName() → "name"），不是字段名。所以：没有 getter 的字段不会出现在 JSON 里；反过来，一个没有对应字段的 getFullName() 也会凭空多出一个 "fullName" 属性。反序列化（@RequestBody）同理，需要无参构造器 + setter。

10.3 控制响应：状态码与响应头

ssh_ch10_ex4
@GetMapping("/france")
public ResponseEntity<Country> france() {
    Country c = Country.of("France", 67);
    return ResponseEntity
            .status(HttpStatus.ACCEPTED)          // 202 而不是默认的 200
            .header("continent", "Europe")
            .header("capital", "Paris")
            .header("favorite_food", "cheese and wine")
            .body(c);
}
什么时候需要 ResponseEntity 直接返回对象时，状态码固定是 200。需要 201 Created、202 Accepted、404 Not Found，或者要塞自定义响应头（分页总数、追踪 ID）时，就包一层 ResponseEntity。

10.4 异常怎么变成 HTTP 响应

业务方法抛异常时，客户端应该收到什么？这一节给出两种方案，请重点看第二种。

ssh_ch10_ex5 · 控制器里 try/catch
@PostMapping("/payment")
public ResponseEntity<?> makePayment() {
  try {
    PaymentDetails d =
        paymentService.processPayment();
    return ResponseEntity
        .status(HttpStatus.ACCEPTED).body(d);
  } catch (NotEnoughMoneyException e) {
    ErrorDetails err = new ErrorDetails();
    err.setMessage("Not enough money…");
    return ResponseEntity
        .badRequest().body(err);
  }
}

✗ 返回类型只能写 <?>，丢掉类型信息
✗ 每个方法都要重复一遍
✗ 业务逻辑被异常处理淹没

ssh_ch10_ex6 · @RestControllerAdvice
@RestController
public class PaymentController {
  @PostMapping("/payment")
  public ResponseEntity<PaymentDetails> makePayment() {
    PaymentDetails d = paymentService.processPayment();
    return ResponseEntity
        .status(HttpStatus.ACCEPTED).body(d);
  }
}

@RestControllerAdvice
public class ExceptionControllerAdvice {
  @ExceptionHandler(NotEnoughMoneyException.class)
  public ResponseEntity<ErrorDetails> handle() {
    ErrorDetails err = new ErrorDetails();
    err.setMessage("Not enough money…");
    return ResponseEntity.badRequest().body(err);
  }
}

✓ 控制器只写正常流程
✓ 一处定义，全局生效
✓ 返回类型精确

10.5 接收请求体：@RequestBody

ssh_ch10_ex7
@PostMapping("/payment")
public ResponseEntity<PaymentDetails> makePayment(
        @RequestBody PaymentDetails paymentDetails) {     // ← JSON 自动反序列化成对象

    logger.info("Received payment " + paymentDetails.getAmount());

    return ResponseEntity.status(HttpStatus.ACCEPTED).body(paymentDetails);
}
curl -X POST http://localhost:8080/payment \
     -H "Content-Type: application/json" \
     -d '{"amount": 1000.0}'
注解数据来自典型 HTTP 方法
@RequestParam查询字符串 ?a=1GET
@PathVariableURL 路径 /users/42全部
@RequestBody请求体（JSON）POST / PUT / PATCH
@RequestHeader请求头全部（第 11 章用到）
GET 不该带请求体 HTTP 规范上 GET 可以有 body，但绝大多数中间件、代理、客户端库都不支持。需要传复杂查询条件时，要么改用 POST，要么把条件拍平成查询参数。

10.6 仓库新增：OpenAPI 契约先行

ssh_ch10_openapi 是书里完全没有的一个工程，展示了当代 REST 开发的主流做法：先写 API 契约，再由工具生成接口代码。

ssh_ch10_openapi · resources/openapi.yml
openapi: 3.0.3
info:
  title: Payment API
  version: 1.0.0
paths:
  /payment:
    post:
      operationId: makePayment
      requestBody:
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/PaymentDetails'
      responses:
        '200':
          description: Payment processed successfully
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/PaymentDetails'
components:
  schemas:
    PaymentDetails:
      type: object
      properties:
        amount:
          type: number
          format: double
ssh_ch10_openapi/pom.xml生成插件
<plugin>
    <groupId>org.openapitools</groupId>
    <artifactId>openapi-generator-maven-plugin</artifactId>
    <version>7.11.0</version>
    <executions><execution><goals><goal>generate</goal></goals>
        <configuration>
            <inputSpec>${project.basedir}/src/main/resources/openapi.yml</inputSpec>
            <generatorName>spring</generatorName>
            <apiPackage>com.example.ssh_ch10_openapi.api</apiPackage>
            <modelPackage>com.example.ssh_ch10_openapi.model</modelPackage>
            <configOptions>
                <interfaceOnly>true</interfaceOnly>      <!-- 只生成接口，实现你自己写 -->
                <useSpringBoot3>true</useSpringBoot3>
            </configOptions>
        </configuration>
    </execution></executions>
</plugin>
ssh_ch10_openapi · PaymentController.java实现生成出来的接口
@RestController
public class PaymentController implements PaymentApi {     // ← PaymentApi 是生成的

    @Override
    public ResponseEntity<PaymentDetails> makePayment(PaymentDetails paymentDetails) {
        logger.info("Received payment " + paymentDetails.getAmount());
        return ResponseEntity.status(HttpStatus.ACCEPTED).body(paymentDetails);
    }
}

这个工程还加了 springdoc-openapi-starter-webmvc-ui，启动后访问 http://localhost:8080/swagger-ui.html 就有一个可以直接点着试的 API 文档页。

本章自测

为什么推荐用 @RestControllerAdvice 而不是在控制器里 try/catch？

三个理由：① 控制器方法能保持精确的返回类型（ResponseEntity<PaymentDetails> 而不是 ResponseEntity<?>）；② 异常到响应的映射规则集中在一处，不会每个控制器写一份还各不相同；③ 业务代码只描述正常流程，可读性大幅提升。这是典型的横切关注点分离——和第 6 章 AOP 是同一个道理。

Jackson 是从哪里来的？我没加过这个依赖。

spring-boot-starter-webmvc 传递引入了 jackson-databind，Boot 的自动配置又注册了一个 MappingJackson2HttpMessageConverter。DispatcherServlet 发现返回值需要写成响应体、且客户端接受 application/json 时，就用这个转换器。整条链路你一行配置都没写——这就是第 7 章说的自动配置。

契约先行（OpenAPI）值得在真实项目里用吗？

取决于团队边界。如果 API 只给自己的前端用、且前后端同一个人写，代码优先 + springdoc 自动生成文档就够了。如果 API 要给别的团队/外部客户用，契约先行的价值很大：契约成为可评审、可版本化的交付物，双方能并行开发，还能自动生成各语言的客户端 SDK。
