Spring 上下文：使用抽象

前三章的鹦鹉例子够简单，但不像真实代码。这一章换成一个真实需求——“发布一条评论”——并且第一次出现接口。你会看到依赖注入真正的威力不在于“少写几个 new”，而在于让高层代码不知道低层用的是哪个实现。

4.1 需求与无框架实现

需求一句话：发布一条评论 = 把它存起来 + 给作者发一条通知。

但“存哪里”（数据库？文件？）和“怎么通知”（邮件？推送？）是会变的。所以我们给这两件事各定义一个接口。

ssh_ch4_ex1纯 Java，没有 Spring
public class CommentService {
    private final CommentRepository commentRepository;
    private final CommentNotificationProxy commentNotificationProxy;

    public CommentService(CommentRepository commentRepository,
                          CommentNotificationProxy commentNotificationProxy) {
        this.commentRepository = commentRepository;
        this.commentNotificationProxy = commentNotificationProxy;
    }

    public void publishComment(Comment comment) {
        commentRepository.storeComment(comment);
        commentNotificationProxy.sendComment(comment);
    }
}

// Main.java —— 所有接线都要手写
var commentRepository = new DBCommentRepository();
var commentNotificationProxy = new EmailCommentNotificationProxy();
var commentService = new CommentService(commentRepository, commentNotificationProxy);
先看清这个基线 ssh_ch4_ex1 的 CommentService 已经是良好设计了：面向接口、构造器注入、字段 final。Spring 并没有改变这个设计，它只是接管了 Main 里那三行 new。这句话是理解整本书的关键。

4.2 哪些类该进上下文

这是新手最常问的问题。判断标准只有一条：Spring 需要管理它吗？

三种写法，同一个结果

ssh_ch4_ex2构造型注解 + 构造器注入（推荐）
@Component
public class DBCommentRepository implements CommentRepository { ... }

@Component
public class EmailCommentNotificationProxy implements CommentNotificationProxy { ... }

@Component
public class CommentService {
    private final CommentRepository commentRepository;
    private final CommentNotificationProxy commentNotificationProxy;

    public CommentService(CommentRepository commentRepository,          // 没有 @Autowired
                          CommentNotificationProxy commentNotificationProxy) {
        this.commentRepository = commentRepository;
        this.commentNotificationProxy = commentNotificationProxy;
    }
    ...
}

@Configuration
@ComponentScan(basePackages = {
        "com.example.proxies", "com.example.repositories", "com.example.services"})
public class ProjectConfiguration { }

ssh_ch4_ex3 把它改成字段注入（@Autowired private CommentRepository ...），ssh_ch4_ex4 则完全不用注解、改在配置类里写 @Bean：

ssh_ch4_ex4三个 @Bean，业务类上一个注解都没有
@Configuration
public class ProjectConfiguration {

    @Bean CommentNotificationProxy commentNotificationProxy() {
        return new EmailCommentNotificationProxy();
    }

    @Bean CommentRepository commentRepository() {
        return new DBCommentRepository();
    }

    @Bean CommentService commentService(CommentRepository commentRepository,
                                        CommentNotificationProxy commentNotificationProxy) {
        return new CommentService(commentRepository, commentNotificationProxy);
    }
}
注意 @Bean 方法的返回类型 写的是接口 CommentRepository 而不是实现类 DBCommentRepository。这样上下文里这个 bean 的类型就是接口类型，注入点按接口找也一定能找到。这是一个小但重要的习惯。

4.3 一个接口有多个实现时

ssh_ch4_ex5 起，CommentNotificationProxy 多了一个实现 CommentPushNotificationProxy。这时 CommentService 的注入点就有两个候选了。

解法一：@Primary（ex5）

@Component
@Primary                                   // 默认用推送
public class CommentPushNotificationProxy implements CommentNotificationProxy { ... }

@Component                                 // 邮件实现还在，但不是默认
public class EmailCommentNotificationProxy implements CommentNotificationProxy { ... }

解法二：@Qualifier（ex6）

仓库这里用了一个比书里更现代的写法：把 @Qualifier 直接标在实现类上，当作“标签”用，而不是依赖 bean 名字。

ssh_ch4_ex6
@Component
@Qualifier("PUSH")                                  // ← 给这个实现贴个标签
public class CommentPushNotificationProxy implements CommentNotificationProxy { ... }

@Component
@Qualifier("EMAIL")
public class EmailCommentNotificationProxy implements CommentNotificationProxy { ... }

@Component
public class CommentService {
    public CommentService(CommentRepository commentRepository,
                          @Qualifier("PUSH") CommentNotificationProxy proxy) {   // ← 按标签要
        ...
    }
}
书中 · 靠 bean 名字
@Component            // bean 名 =
public class CommentPush
       NotificationProxy {}

// 注入点必须写全类名首字母小写
@Qualifier("commentPush
            NotificationProxy")
仓库 · 靠语义标签
@Component
@Qualifier("PUSH")
public class CommentPush
       NotificationProxy {}

// 注入点写业务含义
@Qualifier("PUSH")
为什么这样更好：bean 名字跟类名绑定，重命名类就会悄悄改变行为（注入点的字符串没有编译期检查）。用 @Qualifier("PUSH") 这种语义标签，类名怎么改都不影响；而且标签表达的是“业务意图”，读代码的人一眼知道选的是推送而不是邮件。这是 Spring 官方文档推荐的做法，书里没展开。

4.4 更精确的构造型注解

ssh_ch4_ex7 把 @Component 换成了更有语义的两个：

ssh_ch4_ex7
@Repository
public class DBCommentRepository implements CommentRepository { ... }

@Service
public class CommentService {
    public CommentService(CommentRepository commentRepository,
                          @Qualifier("PUSH") CommentNotificationProxy proxy) { ... }
}

仓库里的测试：验证“接线正确”

仓库给 ex2–ex7 都写了测试，其中最有意思的一个是直接断言注进去的到底是哪个实例：

ssh_ch4_ex6 · AppTests.java
@Test
@DisplayName("Test that CommentService is linked to CommentRepository and CommentNotificationProxy")
void testCommentServiceIsLinkedToDependencies() {
    CommentService service = context.getBean(CommentService.class);
    CommentRepository repository = context.getBean(DBCommentRepository.class);
    CommentNotificationProxy proxy = context.getBean(CommentPushNotificationProxy.class);

    Object injectedRepository = ReflectionTestUtils.getField(service, "commentRepository");
    Object injectedProxy = ReflectionTestUtils.getField(service, "commentNotificationProxy");

    assertSame(repository, injectedRepository);
    assertSame(proxy, injectedProxy);        // 确认注入的是 PUSH 那个实现
}
ReflectionTestUtils Spring Test 提供的工具，用反射读取私有字段。只在测试里用。这里它回答的问题是：“@Qualifier("PUSH") 真的生效了吗？” —— 比打印日志靠谱得多。

动手练习

练习 · 感受解耦

  1. 在 ssh_ch4_ex2 里新增一个 FileCommentRepository implements CommentRepository，加上 @Component，然后运行——观察 NoUniqueBeanDefinitionException。
  2. 用三种方式各修一次这个错：给新实现加 @Primary；给两个实现加 @Qualifier 标签；把新实现的 @Component 去掉。
  3. 对比 ssh_ch4_ex1（无框架）和 ssh_ch4_ex2（Spring）的 CommentService.java——找出它们的差异。答案是：只多了一个 @Component。这就是本章想让你体会的东西。

本章自测

为什么 Comment 不该是 bean？

因为它是数据，不是组件。bean 的默认作用域是单例——整个应用只有一个实例。而评论显然是每条一个对象、随用户输入不断产生的。把数据模型放进上下文既没有意义（没人需要注入一条评论），也会引入危险的共享状态。这条判断在第 5 章讲作用域时会更清楚。

@Service 和 @Component 在功能上有区别吗？

对容器注册来说没有区别——@Service 的定义上就标着 @Component。区别在语义和少数特化行为：@Repository 会开启持久层异常翻译（把 JDBC 的 SQLException 转成 Spring 的 DataAccessException 体系），@Controller 会被 Spring MVC 的处理器映射识别。@Service 目前纯粹是语义标记。

为什么书里强调“面向接口”，而不是直接注入实现类？

Spring 完全允许你注入实现类，代码也能跑。但面向接口给你三样东西：① 换实现不用改调用方；② 测试时可以塞一个假实现或 mock（第 15 章）；③ Spring 用 JDK 动态代理给 bean 加事务/切面时，代理对象实现的是接口——如果你按实现类注入，某些代理场景会直接失败（第 6 章会详细讲这个坑）。
