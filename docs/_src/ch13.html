在 Spring 应用中使用事务

转账要扣一边、加一边。如果中间崩了，钱就凭空消失了。事务的作用是：要么两步都成功，要么一步都不算数。Spring 把这件事简化成了一个注解——但注解背后的机制，正是第 6 章的 AOP。

@Service
public class TransferService {

    private final AccountRepository accountRepository;

    public TransferService(AccountRepository accountRepository) { ... }

    @Transactional                                        // ← 就这一个注解
    public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {

        Account receiver = accountRepository.findAccountById(idReceiver);

        BigDecimal senderNewAmount = sender.getAmount().subtract(amount);
        BigDecimal receiverNewAmount = receiver.getAmount().add(amount);

        accountRepository.changeAmount(idSender, senderNewAmount);
        accountRepository.changeAmount(idReceiver, receiverNewAmount);
    }
}

13.3 三个必须知道的坑

坑一：默认只对运行时异常回滚

坑二：自调用不生效

@Service
public class TransferService {

    public void doTransfer(...) {
        transferMoney(...);        // ✗ this.transferMoney() —— 没经过代理，事务不生效！
    }

    @Transactional
    public void transferMoney(...) { ... }
}
原因和第 6 章一模一样 事务逻辑在代理对象上。this.transferMoney() 是目标对象内部的普通方法调用，压根没经过代理（回看图 13-2 最右边那个框）。
解法：把带 @Transactional 的方法移到另一个 bean 里，从外部调它。
同理，private 方法上的 @Transactional 永远不生效——代理只能拦截 public 方法。

坑三：异常被自己 catch 掉了

@Transactional
public void transferMoney(...) {
    try {
        accountRepository.changeAmount(...);
    } catch (Exception e) {
        logger.error("出错了", e);      // ✗ 异常被吞了，代理什么都没看到 → 照常提交
    }
}

如果你确实想在 catch 里做点事又要回滚，可以手动标记：TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();——但更清爽的做法是把异常重新抛出去。

@Transactional 的常用属性

属性作用常用值
rollbackFor额外指定哪些异常触发回滚Exception.class
readOnly只读事务，可让数据库/驱动做优化查询方法上写 true
propagation已有事务时怎么办REQUIRED（默认，加入）· REQUIRES_NEW（挂起旧的开新的）
timeout超时秒数，超了自动回滚按业务定
isolation隔离级别一般跟数据库默认
放在哪一层 @Transactional 应该标在 Service 层，因为业务上“一个事务”对应的是一个完整用例（转账），而不是一次数据库操作。标在 Repository 上，每个方法一个事务，转账的两步就分成了两个事务——完全失去意义。

本章自测

@Transactional 为什么必须标在 public 方法上？

因为 Spring AOP 通过代理实现事务，而代理（无论是 JDK 动态代理还是 CGLIB 子类）都只能拦截 public 方法——private 方法不可重写，protected/包级方法 CGLIB 虽能拦截但 Spring 默认不处理。标在 private 方法上不会报错，只是静悄悄地不生效，这比报错更危险。

为什么默认只对非受检异常回滚？

历史约定，继承自 EJB 的默认行为。背后的假设是：受检异常代表“预期内、调用方应该处理的业务情况”（比如“余额不足”），既然是预期内的，事务可能仍应提交；非受检异常代表“意料之外的故障”，应该回滚。这个假设在现代代码里往往不成立，所以很多团队直接约定所有 @Transactional 都写 rollbackFor = Exception.class。

事务和第 6 章的 AOP 是什么关系？

事务就是用 AOP 实现的。@EnableTransactionManagement（Boot 自动开启）会注册一个事务拦截器，它本质上是一个 @Around 通知：前置逻辑开事务、调用 proceed()、正常返回则提交、抛非受检异常则回滚。所以 AOP 的所有限制（自调用失效、只拦 public 方法、目标必须是 bean）在事务上原样成立。
