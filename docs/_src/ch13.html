在 Spring 应用中使用事务

转账要扣一边、加一边。如果中间崩了，钱就凭空消失了。事务的作用是：要么两步都成功，要么一步都不算数。Spring 把这件事简化成了一个注解——但注解背后的机制，正是第 6 章的 AOP。

本章工程 ssh_ch13_ex1 转账正常流程 · ssh_ch13_ex2 转账过程中故意抛异常，验证回滚

13.1 为什么需要事务

ACID：事务承诺的四件事

原子性只是事务四个特性中的一个。面试和数据库文档里它们总是一起出现，合称 ACID：

特性承诺放到转账例子里
Atomicity 原子性一组操作要么全做，要么全不做不会出现 Helen 扣了钱而 Peter 没收到
Consistency 一致性事务前后，数据都满足业务规则和数据库约束两人余额之和始终是 2000；余额不为负（需要你用约束或代码来定义规则）
Isolation 隔离性并发的事务互不干扰，效果如同一个接一个执行两笔转账同时发生，不会互相读到对方改了一半的余额
Durability 持久性一旦提交，结果不会因为崩溃或断电而丢失接口返回成功后服务器立刻断电，重启后余额仍是转账后的值

本章的两个工程只演示了原子性。持久性由数据库负责，你不用写代码。隔离性是最容易被忽略的一个，它有级别之分，见后面“常用属性”一节。

13.2 Spring 事务的工作机制

ssh_ch13_ex1 · services/TransferService.java
@Service
public class TransferService {

    private final AccountRepository accountRepository;

    public TransferService(AccountRepository accountRepository) { ... }

    @Transactional                                        // ← 就这一个注解
    public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {
        Account sender = accountRepository.findAccountById(idSender);
        Account receiver = accountRepository.findAccountById(idReceiver);

        BigDecimal senderNewAmount = sender.getAmount().subtract(amount);
        BigDecimal receiverNewAmount = receiver.getAmount().add(amount);

        accountRepository.changeAmount(idSender, senderNewAmount);
        accountRepository.changeAmount(idReceiver, receiverNewAmount);
    }
}

13.3 三个必须知道的坑

坑一：默认只对运行时异常回滚

坑二：自调用不生效

@Service
public class TransferService {

    public void doTransfer(...) {
        transferMoney(...);        // ✗ this.transferMoney() —— 没经过代理，事务不生效！
    }

    @Transactional
    public void transferMoney(...) { ... }
}
原因和第 6 章一模一样 事务逻辑在代理对象上。this.transferMoney() 是目标对象内部的普通方法调用，压根没经过代理（回看图 13-2 最右边那个框）。
解法：把带 @Transactional 的方法移到另一个 bean 里，从外部调它。
同理，private 方法上的 @Transactional 永远不生效——代理是靠“生成子类并重写方法”来拦截的，private 方法无法被重写。

坑三：异常被自己 catch 掉了

@Transactional
public void transferMoney(...) {
    try {
        accountRepository.changeAmount(...);
    } catch (Exception e) {
        logger.error("出错了", e);      // ✗ 异常被吞了，代理什么都没看到 → 照常提交
    }
}

如果你确实想在 catch 里做点事又要回滚，可以手动标记：TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();——但更清爽的做法是把异常重新抛出去。

隔离级别：并发事务能互相看到多少

完全隔离代价很高（事务要排队），所以数据库提供了四个级别，让你在正确性和并发性能之间选。级别越高，能防住的并发问题越多，也越慢。

isolation =脏读不可重复读幻读谁的默认值
READ_UNCOMMITTED会会会—
READ_COMMITTED不会会会PostgreSQL、Oracle、H2
REPEATABLE_READ不会不会标准上会MySQL（InnoDB）
SERIALIZABLE不会不会不会—
  • 脏读：读到别的事务还没提交的数据，而对方后来回滚了。
  • 不可重复读：同一个事务里两次读同一行，结果不一样，因为中间有别的事务改了它并提交了。
  • 幻读：同一个事务里两次按条件查询，第二次多出或少了几行，因为中间有别的事务插入或删除了数据。
本章的转账代码在并发下其实不安全 transferMoney 先读余额、在 Java 里算出新值、再写回去。两笔从 Helen 转出的转账同时进来，可能都读到 1000，各自写回 900，Helen 只被扣了一次。@Transactional 默认的隔离级别挡不住这种“丢失更新”。常见解法有三种：把计算交给数据库（UPDATE account SET amount = amount - ? WHERE id = ?）；读的时候加行锁（SELECT … FOR UPDATE）；或者用版本号做乐观锁。书里为了突出事务本身没有展开，但写真实的金额逻辑时必须考虑。
放在哪一层 @Transactional 应该标在 Service 层，因为业务上“一个事务”对应的是一个完整用例（转账），而不是一次数据库操作。标在 Repository 上，每个方法一个事务，转账的两步就分成了两个事务——完全失去意义。

本章自测

@Transactional 能标在哪些可见性的方法上？

取决于代理类型。Spring AOP 通过代理实现事务：private 方法永远不行——它不能被子类重写，代理拦不到，而且不会报错，只是静悄悄地不生效，这比报错更危险。public 方法永远可以。中间的 protected / 包级方法：书里那个年代（Spring 5）一律不处理；Spring 6 起，只要用的是基于类的代理（CGLIB，Boot 的默认方式）就也能生效，基于接口的 JDK 动态代理则仍然只认 public。稳妥的习惯没变：事务方法写成 public，并且从别的 bean 调它。

为什么默认只对非受检异常回滚？

历史约定，继承自 EJB 的默认行为。背后的假设是：受检异常代表“预期内、调用方应该处理的业务情况”（比如“余额不足”），既然是预期内的，事务可能仍应提交；非受检异常代表“意料之外的故障”，应该回滚。这个假设在现代代码里往往不成立，所以很多团队直接约定所有 @Transactional 都写 rollbackFor = Exception.class。

事务和第 6 章的 AOP 是什么关系？

事务就是用 AOP 实现的。@EnableTransactionManagement（Boot 自动开启）会注册一个事务拦截器，它本质上是一个 @Around 通知：前置逻辑开事务、调用 proceed()、正常返回则提交、抛非受检异常则回滚。所以 AOP 的所有限制（自调用失效、private 方法拦不到、目标必须是 bean）在事务上原样成立。
