7.2 Spring Boot 到底做了什么

“魔法”其实只有三件事，拆开看一点也不神秘。

父 POM 与 starter

ssh_ch7_ex1/pom.xml全部内容，就这么点
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.0.4</version>
</parent>

<properties>
    <java.version>25</java.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>   <!-- 注意没有版本号 -->
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>

依赖不写版本号，是因为父 POM 里已经声明了一整套经过兼容性验证的版本。这就是“依赖管理”的价值。

书中 · Boot 2.3.4
spring-boot-starter-web
spring-boot-starter-test

两个“大 starter”，一个把整个 Web 栈全带上，一个把所有测试库全带上。

仓库 · Boot 4.0.4
spring-boot-starter-webmvc
spring-boot-starter-webmvc-test

按技术切分的模块化 starter，各自只带需要的东西。

为什么变：Spring Boot 4 做了一次 starter 大重构。过去 spring-boot-starter-web 含义含糊（到底是 Servlet 栈还是响应式栈？），现在拆成 -webmvc（Servlet/阻塞）和 -webflux（响应式）；测试 starter 也不再是一个巨无霸，而是跟着功能 starter 走（-webmvc-test、-jdbc-test、-data-jdbc-test）。
实际影响：书里所有 spring-boot-starter-web 在本仓库都写作 spring-boot-starter-webmvc。写成旧名字通常也能跑（Boot 4 保留了兼容 artifact），但会带进多余依赖，建议跟仓库保持一致。
版本分布 仓库里的 Boot 版本不是完全统一的：第 7–8 章是 4.0.4/4.0.5，第 9–10、12–13 章是 4.0.6，第 11、14 章是 4.1.0；ssh_ch10_ex5 是唯一一个例外，还停在 3.4.1 + 旧的 spring-boot-starter-web（应该是升级时漏掉的）。这不影响学习，但你如果照着某个工程抄 pom，记得看清楚它是哪一版。

7.3 第一个网页

ssh_ch7_ex1 · Main.java
@SpringBootApplication
public class Main {
    public static void main(String[] args) {
        SpringApplication.run(Main.class, args);
    }
}
@SpringBootApplication = 三个注解 @Configuration（这是个配置类）+ @ComponentScan（扫描当前包及子包）+ @EnableAutoConfiguration（开启自动配置）。
第二点很关键：Boot 工程不用手写 @ComponentScan(basePackages=...)，但你的所有类必须放在 Main 所在包的下面，否则扫不到。这是 Boot 新手第一大坑。
ssh_ch7_ex1 · controllers/MainController.java
@Controller
public class MainController {

    @GetMapping("/home")
    public String home() {
        return "home.html";      // 返回的是视图名，不是响应内容
    }
}
ssh_ch7_ex1 · src/main/resources/static/home.html
<!DOCTYPE html>
<html lang="en">
<head><meta charset="UTF-8"><title>Home Page</title></head>
<body><h1>Welcome!</h1></body>
</html>
static 还是 templates？ 本章页面放在 resources/static/——因为它是静态 HTML，没有任何动态内容。
第 8 章开始用 Thymeleaf 后，页面必须放到 resources/templates/。放错目录会得到 404 或者页面原样输出 ${username}，是极常见的错误。
书中
@RequestMapping("/home")
public String home() { ... }
仓库
@GetMapping("/home")
public String home() { ... }
为什么变：@GetMapping 是 @RequestMapping(method = GET) 的快捷写法（Spring 4.3 引入）。仓库统一用了语义更明确的 @GetMapping/@PostMapping。ssh_ch8_ex5 里作者还特意把旧写法用注释保留在旁边，方便对照。

7.4 外部化配置：application.properties

每个 Boot 工程的 src/main/resources/ 下都有一份 application.properties。第 7 章这份里只有一行应用名，但从第 11 章起它开始承担真正的工作，这里先把规则讲清楚。书里没有单独讲这部分，是按用到的顺序零散出现的。

两类属性

Boot 认识的属性你自己定义的属性
谁来读自动配置类你的代码
仓库里的例子server.port=9090（第 11 章）
spring.datasource.url=…（第 12 章）
spring.sql.init.mode=always（第 12 章）		payments.url（第 11 章）
custom.datasource.url（第 12 章）
怎么生效写上就生效要用 @Value 或 @ConfigurationProperties 取出来

@Value：把一个属性注入进来

ssh_ch11_ex1 · proxies/PaymentsProxy.java第 11 章会见到
public PaymentsProxy(@Value("${payments.url:http://localhost:8080}") String paymentsUrl) {
    this.restClient = RestClient.create(paymentsUrl);
}

${payments.url:http://localhost:8080} 读作：取属性 payments.url 的值；冒号后面是默认值，属性没配时用它。不写默认值而属性又不存在，应用会启动失败，这通常是你想要的（配置缺失应该尽早暴露）。第 12 章 ssh_ch12_ex3 的 @Value("${custom.datasource.url}") 就是不带默认值的写法。

同一个属性可以从多处给，谁的优先级高

# ① 写在 application.properties 里（优先级最低）
server.port=9090

# ② 环境变量：点和横线换成下划线，全大写
SERVER_PORT=9091 ./mvnw spring-boot:run

# ③ 命令行参数（优先级最高）
./mvnw package -DskipTests
java -jar target/ssh_ch7_ex1-0.0.1-SNAPSHOT.jar --server.port=9092

优先级从低到高：properties 文件 → 环境变量 → 命令行参数。这个设计的目的是同一个 jar 不改代码、不重新打包，就能部署到不同环境：开发机用文件里的默认值，服务器上用环境变量覆盖数据库地址和密码。

顺带学会了打包 上面第 ③ 种用到了 ./mvnw package：它借助 spring-boot-maven-plugin 把应用、所有依赖和内嵌 Tomcat 打成一个可执行 jar，有 JDK 的机器上 java -jar 就能跑。这就是 Boot 应用最基本的部署方式。

Profile：给不同环境各备一份配置

# application.properties —— 所有环境共用
spring.application.name=demo

# application-dev.properties —— 只在 dev profile 下加载
spring.datasource.url=jdbc:h2:mem:devdb

# application-prod.properties —— 只在 prod profile 下加载
spring.datasource.url=jdbc:mysql://db.internal/app

用 --spring.profiles.active=prod（或环境变量 SPRING_PROFILES_ACTIVE=prod）选择激活哪一份。仓库的示例都很小，没有用到 profile；真实项目几乎都会用。

@ConfigurationProperties：属性一多就该用它

仓库里没有对应工程作为 @Value 的进阶写法了解
@ConfigurationProperties(prefix = "payments")
public record PaymentsProperties(String url, Duration timeout) { }

// 主类或任一配置类上：
@EnableConfigurationProperties(PaymentsProperties.class)

// application.properties：
// payments.url=http://localhost:8080
// payments.timeout=2s

它把同一前缀下的一组属性绑定成一个类型安全的对象，可以像普通 bean 一样构造器注入。相比到处散落的 @Value 字符串，好处是属性集中在一处、有类型转换（上面的 2s 直接变成 Duration）、IDE 能补全。经验法则：一两个属性用 @Value，三个以上或成组出现就用 @ConfigurationProperties。

properties 还是 yml application.yml 和 application.properties 功能等价，只是语法不同（yml 用缩进表达层级）。仓库统一用 properties，唯一的 yml 是第 10 章的 openapi.yml，那是 API 契约，不是 Spring 配置。

仓库自带的测试

ssh_ch7_ex1 · MainTests.java
@SpringBootTest
class MainTests {

    @Autowired private WebApplicationContext webApplicationContext;
    private MockMvc mockMvc;

    @BeforeEach
    void setUp() {

本章自测

Spring Boot 是怎么“猜”到我要用 Tomcat 的？

自动配置类里写满了条件判断，形如“如果 classpath 上存在 org.apache.catalina.startup.Tomcat 这个类，并且用户没有自己定义 ServletWebServerFactory bean，就注册一个 Tomcat 工厂”。因为 spring-boot-starter-webmvc 传递引入了 tomcat-embed-core，条件成立。想换 Jetty，就在依赖里排除 Tomcat 再加 Jetty starter——条件判断自然会走向另一条分支。

为什么控制器方法返回的字符串会变成一个页面？

因为 @Controller（不带 @ResponseBody）的返回值被当作视图名处理：DispatcherServlet 拿着这个名字去问视图解析器“哪个文件对应它”，找到后渲染成 HTML 写进响应。如果类上是 @RestController，返回值则直接被当成响应体写出去——这正是第 10 章的主题。

spring-boot-starter-web 和 spring-boot-starter-webmvc 能混用吗？

在 Boot 4 里两者都还能解析，但含义已经收敛：-webmvc 明确表示传统的 Servlet 阻塞式 Web 栈。仓库统一用 -webmvc，你自己新建工程时（比如从 start.spring.io 生成）也会拿到这个名字。书里的 -web 写法照抄到 Boot 4 工程里通常能跑，但不是现在的推荐写法。
