Spring 上下文：装配 bean

上一章把对象放进了池子，但它们互不相识。这一章解决“怎么让 A 拿到 B”——也就是依赖注入。方式有五种，看起来很多，其实只有两大类：在配置类里连线，和让 Spring 自己连线。

本章工程 ssh_ch3_ex1 没连线（反例）· ex2 方法直接调用 · ex3 @Bean 方法参数 · ex4 @Autowired 字段 · ex5 @Autowired 构造器 · ex6 @Autowired setter · ex7 构造器循环依赖（会崩）· ex8 @Qualifier 在 @Bean 参数上 · ex9 @Qualifier 在构造器参数上

3.1 先看反例：不连线会怎样

ssh_ch3_ex1 · ProjectConfig.java
@Bean
public Parrot parrot() { Parrot p = new Parrot(); p.setName("Koko"); return p; }

@Bean
public Person person() { Person p = new Person(); p.setName("Ella"); return p; }
// 注意：没有 p.setParrot(...)
Person's name: Ella
Parrot's name: Koko
Person's parrot: null   ← 两个 bean 都在上下文里，但彼此没有关系

“在同一个上下文里”不等于“互相引用”。关系必须显式建立。

3.2 在配置类里连线

方式 A：直接调用 @Bean 方法

ssh_ch3_ex2 · ProjectConfig.java
@Bean
public Parrot parrot() { Parrot p = new Parrot(); p.setName("Koko"); return p; }

@Bean
public Person person() {
    Person p = new Person();
    p.setName("Ella");
    p.setParrot(parrot());     // ← 直接调另一个 @Bean 方法
    return p;
}

这里有一个非常值得停下来想的问题：parrot() 被调用了两次（一次是容器创建 parrot bean，一次是 person() 里手动调），为什么上下文里只有一个 Parrot 实例？

方式 B：用 @Bean 方法参数（推荐）

ssh_ch3_ex3 · ProjectConfig.java
@Bean
public Parrot parrot() { ... }

@Bean
public Person person(Parrot parrot) {    // ← 让 Spring 把 parrot bean 递进来
    Person p = new Person();
    p.setName("Ella");
    p.setParrot(parrot);
    return p;
}
为什么这种更好 它不依赖“配置类被代理”这个隐式机制，意图更直白：这个 bean 需要一个 Parrot，从上下文里找一个给我。而且它对 @Bean 方法所在的类是不是配置类不敏感，重构时更安全。

3.3 让 Spring 自己连线：@Autowired

当两个类都是 @Component（不需要在配置类里写创建逻辑）时，用 @Autowired。它能放在三个位置。

只有一个构造器时可以省略 @Autowired Spring 4.3 起，如果类只有一个构造器，@Autowired 可以不写。仓库第 4 章之后的代码全是这种写法： 
@Service
public class CommentService {
    private final CommentRepository commentRepository;

    public CommentService(CommentRepository commentRepository) {   // 没有 @Autowired
        this.commentRepository = commentRepository;
    }
}

3.4 循环依赖：一定要认识的报错

ssh_ch3_ex7这个工程跑起来会失败——这是故意的
@Component
public class Person {
    private Parrot parrot;
    public Person(Parrot parrot) { this.parrot = parrot; }   // Person 要 Parrot
}

@Component
public class Parrot {
    private Person person;
    public Parrot(Person person) { this.person = person; }   // Parrot 又要 Person
}
纯 Spring 和 Spring Boot 在这里不一样 Spring Framework 本身（包括 7.0）仍然允许字段 / setter 注入的循环依赖：容器先用构造器把对象造出来，把这个“半成品”的引用提前暴露（三级缓存），再回头填字段，于是环被解开。只有构造器 ↔ 构造器的环无解，这正是 ssh_ch3_ex7 演示的情况。
Spring Boot 2.6 起默认禁止了所有循环依赖，字段注入的环也会启动失败，除非显式写 spring.main.allow-circular-references=true。所以同样的代码，放在第 3 章这种纯 spring-context 工程里能跑，搬到第 7 章以后的 Boot 工程里就会报错。
还有一个顺序细节：一边构造器、一边字段的“混合环”能不能解开，取决于谁先被创建。先创建的那个 bean 必须是字段注入的一方（它能先造出半成品）；如果先创建的是构造器注入的一方，照样报 BeanCurrentlyInCreationException。下面的练习 2 会让你两种都看到。

正确做法从来不是打开开关，而是重新设计：抽出第三个类承担共同职责，或者把其中一个方向改成事件/回调。

3.5 多个候选 bean 时，Spring 怎么选

这是本章最实用的一节。当注入点的类型对应多个 bean 时，Spring 按下面的顺序决策：

@Qualifier 的两个用法

ssh_ch3_ex8标在 @Bean 方法的参数上
@Bean public Parrot parrot1() { ... "Koko" ... }
@Bean public Parrot parrot2() { ... "Miki" ... }

@Bean
public Person person(@Qualifier("parrot2") Parrot parrot2) {
    Person p = new Person();
    p.setParrot(parrot2);          // 明确要 Miki
    return p;
}
ssh_ch3_ex9标在 @Component 类的构造器参数上
@Component
public class Person {
    private Parrot parrot;

    public Person(@Qualifier("parrot2") Parrot parrot) {
        this.parrot = parrot;
    }
}

ssh_ch3_ex9 还展示了一个容易忽略的能力：@ComponentScan 和 @Bean 可以在同一个配置类里共存——Person 靠扫描进上下文，两只 Parrot 靠 @Bean 方法进上下文。

与书中的差异

书中
  • Spring 5.2，字段/setter 循环依赖默认允许
  • public static void main(String[] args)
  • 示例包名 com.example，工程名 sq-ch3-ex1
仓库
  • Spring 7，字段/setter 循环依赖仍然允许（只有 Boot 工程默认禁止）
  • static void main()（Java 25）
  • 工程名 ssh_ch3_ex1，每个工程带 JUnit 5 测试
本章代码本身几乎没变。依赖注入的 API 从 Spring 4 到 Spring 7 一直稳定，这是 Spring 生态最保值的部分——你在这一章学的东西十年后大概率还能用。

动手练习

练习 · 让循环依赖真的报错

  1. 运行 ssh_ch3_ex7，完整读一遍堆栈，找到 BeanCurrentlyInCreationException 那一行。
  2. 把 Parrot 的构造器注入改成 @Autowired 字段注入，再跑一次——这次能正常启动并打印 Person's parrot: Parrot: Koko：Spring 先造出 Parrot 的半成品，再拿它去构造 Person。然后把 Parrot 改回构造器注入、换成给 Person 用字段注入——又失败了，因为扫描时先创建的是 Parrot，它的构造器在等一个还造不出来的 Person。
  3. 把 ssh_ch3_ex8 里的 @Qualifier("parrot2") 删掉，观察 Spring 如何按参数名 parrot2 兜底匹配成功；再把参数名改成 p，观察它开始报错。

本章自测

为什么在 @Configuration 类里直接调用 parrot() 不会创建两个实例？

因为 @Configuration 类会被 CGLIB 代理成子类，@Bean 方法被重写成“先查上下文缓存”的版本（图 3-1）。如果把 @Configuration 换成 @Component，这个代理不生效，parrot() 就是一次真实的方法调用，会造出第二个实例——这个差别叫 full mode vs lite mode。

@Primary 和 @Qualifier 该用哪个？

方向不同：@Primary 由 bean 的定义方声明“我是默认选择”，全局生效，一个类型只能有一个；@Qualifier 由 注入点声明“我要哪一个”，局部生效，可以有任意多个。典型组合是：给最常用的实现打 @Primary，少数需要别的实现的地方用 @Qualifier 覆盖。第 4 章 ssh_ch4_ex5 和 ex6 正好演示了这两条路。

为什么构造器注入比字段注入好？

四个理由：① 字段能声明成 final，对象不可变；② 对象构造完成即处于完整可用状态，不存在依赖为 null 的中间态；③ 单元测试里可以直接 new Service(mockRepo)，不需要反射或 Spring 容器（第 15 章会用到）；④ 构造器参数一多就很刺眼，天然提醒你这个类职责过重。
