用 Spring Data 实现持久化

第 12 章你手写了 SQL 和 RowMapper。这一章把它们也删掉——你只声明一个接口，Spring Data 生成实现。这和第 11 章 OpenFeign 的套路完全一样：契约由你写，实现由框架给。

本章工程 ssh_ch14_ex1 —— 把第 13 章的转账应用从 JdbcTemplate 改写成 Spring Data JDBC。对照读这两个工程收获最大。

实体：加一个 @Id

ssh_ch14_ex1 · model/Account.java
public class Account {

    @Id                          // org.springframework.data.annotation.Id
    private long id;
    private String name;
    private BigDecimal amount;
    // getter / setter ...
}
别 import 错了 Spring Data JDBC 用的是 org.springframework.data.annotation.Id，不是 JPA 的 jakarta.persistence.Id。IDE 自动补全时很容易选错，选错了实体识别不了主键。
另外注意：类名 Account 会被自动映射到表名 account，字段名 amount 映射到列 amount。要自定义映射用 @Table 和 @Column。

省掉的东西：@Repository 注解（接口会被 Spring Data 自动发现并注册）、RowMapper 实现类、所有 CRUD 的 SQL 和方法体。只有真正非标准的查询才需要你写 @Query。

Spring Data 是怎么生成实现的

派生查询：方法名就是查询

ssh_ch14_ex1 用了 @Query 显式写 SQL，但对简单查询你连 SQL 都不用写：

方法名生成的查询条件
findByName(String name)WHERE name = ?
findByNameAndAmount(String n, BigDecimal a)WHERE name = ? AND amount = ?
findByAmountGreaterThan(BigDecimal a)WHERE amount > ?
findByNameContaining(String s)WHERE name LIKE %?%
findByNameOrderByAmountDesc(String n)WHERE name = ? ORDER BY amount DESC
countByName(String name)SELECT count(*) … WHERE name = ?
派生查询的代价 方法名一长就变得没法读（findByNameAndAmountGreaterThanAndCreatedDateBetweenOrderByAmountDesc），而且字段改名后方法名不改就会在启动时报错（这其实是好事，编译期发现总比运行时好）。经验法则：两三个条件以内用派生查询，再复杂就写 @Query。

@Modifying 不能忘

@Modifying                  // ← 告诉 Spring Data：这是写操作，不是查询
@Query("UPDATE account SET amount = :amount WHERE id = :id")
void changeAmount(long id, BigDecimal amount);

不加 @Modifying，Spring Data 会把这条 UPDATE 当成查询、用 executeQuery 去执行，数据库驱动会直接拒绝：H2 下报 Method is only allowed for a query. Use execute or executeUpdate instead of executeQuery，Spring 把它包成 UncategorizedSQLException，接口返回 500，余额不变。

Service 层的变化

ssh_ch14_ex1 · services/TransferService.java
@Transactional
public void transferMoney(long idSender, long idReceiver, BigDecimal amount) {
    Account sender = accountRepository.findById(idSender)
            .orElseThrow(() -> new AccountNotFoundException());     // ← 返回 Optional

    Account receiver = accountRepository.findById(idReceiver)
            .orElseThrow(() -> new AccountNotFoundException());

    accountRepository.changeAmount(idSender, sender.getAmount().subtract(amount));
    accountRepository.changeAmount(idReceiver, receiver.getAmount().add(amount));
}
Optional 是个改进 第 13 章的 jdbc.queryForObject() 查不到时直接抛 EmptyResultDataAccessException；CrudRepository.findById() 返回 Optional<Account>，让"没找到"变成一个你必须显式处理的正常分支，而不是异常。仓库这里配合自定义的 AccountNotFoundException，语义清楚多了。

本章自测

为什么 AccountRepository 不需要 @Repository 注解？

因为 Spring Data 的 repository 扫描机制会自动找出所有继承了 Repository 体系的接口，为它们生成代理实现并注册成 bean。Boot 的自动配置默认扫描主类所在包及子包。加上 @Repository 也没坏处，但是多余的。

Spring Data JDBC 和 Spring Data JPA 该选哪个？

Spring Data JDBC：把对象直接映射成 SQL，没有会话、没有脏检查、没有延迟加载——你写的每个方法调用对应可预测的 SQL。适合领域模型简单、想掌控 SQL 的项目。
Spring Data JPA（Hibernate）：功能强得多（关联映射、二级缓存、乐观锁），但也带来复杂度（N+1 查询、LazyInitializationException、脏检查何时刷库）。团队熟悉 JPA、领域模型复杂时选它。
本书选 JDBC 是教学考虑，不是说 JPA 不好。

派生查询会不会在运行时才发现写错了？

不会。Spring Data 在应用启动时就解析所有 repository 方法名，解析不出来（比如实体上没有那个字段）直接启动失败并给出明确报错。这是"快速失败"的好设计——比上线后某个接口一调就崩强得多。
