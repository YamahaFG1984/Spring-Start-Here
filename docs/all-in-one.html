1.1 为什么要用框架

作者在书的开篇用了一个冰山比喻，我觉得它是整本书最值钱的一张图。用户看到的是“业务逻辑”——下单、转账、发评论；但真正撑起一个企业级应用的代码，绝大部分在水面以下，而且跟你的业务没有一点关系。

所以“用框架”这个决定的本质是：用一点点自由度，换掉一大堆重复且容易写错的基础设施代码。Spring 之所以在 Java 世界占了半壁江山，是因为它把水下这块拆成了可以按需取用的模块，而不是一个必须整体吞下的庞然大物。

什么时候不该用框架

  • 包体积必须极小：框架带来的依赖树可能比你的业务代码大一个数量级。
  • 安全要求必须完全自研：不能接受“信任第三方代码”的场景（少见，但存在）。
  • 已有大量定制：如果你已经把框架的每个扩展点都改写了，说明框架跟需求不匹配，维护成本反而更高。
  • 迁移收益不足：一个能跑十年的老系统，为了“用上新框架”而重写，通常是负收益。

本章自测

Spring Boot 和 Spring Framework 是什么关系？

Spring Boot 不是替代品，而是建立在 Spring Framework 之上的一层“约定优于配置”工具：它提供起步依赖（把一组常用依赖打包成一个）、自动配置（根据 classpath 上有什么来推断该注册哪些 bean）、内嵌服务器和外部化配置。你在第 2–6 章学的容器知识，在 Boot 项目里一字不差地成立。

为什么这本书要用 5 章讲“上下文”？

因为后面所有能力都是通过“往上下文里放 bean、让 Spring 用代理包装它们”实现的。@Transactional 生效靠代理（第 6 章 AOP + 第 13 章），@RequestScope 生效靠作用域（第 5 章 + 第 9 章），Spring Data 的 Repository 是容器动态生成的 bean（第 14 章）。跳过第 2–6 章，后面每一个特性都会像魔法。

本仓库为什么把书里 15 章的内容拆成了 16 章？

第 2 版把原第 15 章“测试你的 Spring 应用”拆成了两章：第 15 章讲纯单元测试（不启动 Spring，用 Mockito 手工装配），第 16 章讲 Spring 集成测试（启动上下文、@SpringBootTest、@MockitoBean、MockMvc）。仓库里对应的 commit 就叫 CH15 和 CH16，它们没有新建工程，而是往 ssh_ch14_ex1 和 ssh_ch9_ex1 里加了测试类。

2.2 方式一：@Bean 方法

ssh_ch2_ex2 · config/ProjectConfig.java
@Configuration
public class ProjectConfig {

    @Bean
    Parrot parrot() {          // ← 方法名就是 bean 的名字
        var p = new Parrot();
        p.setName("Koko");
        return p;
    }

    @Bean
    String hello() { return "Hello"; }   // 任何类型都能当 bean

    @Bean

ssh_ch2_ex2 · Main.java
var context = new AnnotationConfigApplicationContext(ProjectConfig.class);

Parrot p = context.getBean(Parrot.class);   // 按类型取
System.out.println(p.getName());            // Koko
System.out.println(context.getBean(String.class));   // Hello
System.out.println(context.getBean(Integer.class));  // 10

三条规则，记住就够用：

  1. @Configuration 标记“这是一个配置类”，把它传给 AnnotationConfigApplicationContext 的构造器。
  2. 方法上的 @Bean 表示“把返回值放进上下文”。方法只在容器启动时被调一次（单例，见第 5 章）。
  3. 方法名 = bean 名。也可以写 @Bean(name = "miki") 覆盖。
可以放任何类型 String 和 Integer 也能当 bean。这不是玩笑——第 12 章的 DataSource、第 6 章的切面对象，本质上都是这样注册进去的。

@Bean 方法会被调用几次？

默认作用域是单例，所以整个上下文生命周期内只调用一次，返回值被缓存起来。第 5 章会看到把它改成 @Scope(BeanDefinition.SCOPE_PROTOTYPE) 后，每次 getBean 都会重新调用。这个细节也是第 3 章“方法直接调用能装配 bean”能成立的原因。

本章自测

为什么在 @Configuration 类里直接调用 parrot() 不会创建两个实例？

因为 @Configuration 类会被 CGLIB 代理成子类，@Bean 方法被重写成“先查上下文缓存”的版本（图 3-1）。如果把 @Configuration 换成 @Component，这个代理不生效，parrot() 就是一次真实的方法调用，会造出第二个实例——这个差别叫 full mode vs lite mode。

@Primary 和 @Qualifier 该用哪个？

方向不同：@Primary 由 bean 的定义方声明“我是默认选择”，全局生效，一个类型只能有一个；@Qualifier 由 注入点声明“我要哪一个”，局部生效，可以有任意多个。典型组合是：给最常用的实现打 @Primary，少数需要别的实现的地方用 @Qualifier 覆盖。第 4 章 ssh_ch4_ex5 和 ex6 正好演示了这两条路。

为什么构造器注入比字段注入好？

四个理由：① 字段能声明成 final，对象不可变；② 对象构造完成即处于完整可用状态，不存在依赖为 null 的中间态；③ 单元测试里可以直接 new Service(mockRepo)，不需要反射或 Spring 容器（第 15 章会用到）；④ 构造器参数一多就很刺眼，天然提醒你这个类职责过重。

本章自测

为什么 Comment 不该是 bean？

因为它是数据，不是组件。bean 的默认作用域是单例——整个应用只有一个实例。而评论显然是每条一个对象、随用户输入不断产生的。把数据模型放进上下文既没有意义（没人需要注入一条评论），也会引入危险的共享状态。这条判断在第 5 章讲作用域时会更清楚。

@Service 和 @Component 在功能上有区别吗？

对容器注册来说没有区别——@Service 的定义上就标着 @Component。区别在语义和少数特化行为：@Repository 会开启持久层异常翻译（把 JDBC 的 SQLException 转成 Spring 的 DataAccessException 体系），@Controller 会被 Spring MVC 的处理器映射识别。@Service 目前纯粹是语义标记。

为什么书里强调“面向接口”，而不是直接注入实现类？

Spring 完全允许你注入实现类，代码也能跑。但面向接口给你三样东西：① 换实现不用改调用方；② 测试时可以塞一个假实现或 mock（第 15 章）；③ Spring 用 JDK 动态代理给 bean 加事务/切面时，代理对象实现的是接口——如果你按实现类注入，某些代理场景会直接失败（第 6 章会详细讲这个坑）。

本章自测

为什么单例 bean 不能有可变字段？

因为在 web 应用里，同一个单例 bean 会被多个 HTTP 请求线程并发调用。实例字段是共享的，一个线程写、另一个线程读，就会读到别人的数据（图 5-3 上半部分演示的正是这个）。方法内的局部变量在各自线程栈上，没有这个问题。真需要请求级状态，用第 9 章的 @RequestScope。

为什么给单例注入原型，原型就“失效”了？

因为依赖注入发生在单例被创建的那一刻，且只发生一次。那一次注入确实向上下文要了一个新的原型实例，但之后单例的字段就一直指着它。要让原型真正每次都新，就必须每次调用时重新去要——ApplicationContext.getBean()、ObjectProvider、或作用域代理，三条路都是在做这件事。

@Scope("prototype")、BeanDefinition.SCOPE_PROTOTYPE、ConfigurableBeanFactory.SCOPE_PROTOTYPE 有区别吗？

没有。三者的值都是字符串 "prototype"。书里用第三种，仓库用第二种，纯粹是写法偏好。用常量而不是裸字符串的好处是防拼写错误。

6.1 Spring 怎么做到“拦截”的

先解决一个疑问：CommentService 是你写的普通类，你没有在里面写任何日志代码，Spring 凭什么能在它的方法前后插入逻辑？

6.2 写第一个切面

ssh_ch6_ex1 · aspects/LoggingAspect.java
@Aspect
public class LoggingAspect {

    private final Logger logger = Logger.getLogger(LoggingAspect.class.getName());

    @Around("execution(* com.example.services.*.*(..))")
    public void log(ProceedingJoinPoint joinPoint) throws Throwable {
        logger.info("Method will execute");
        joinPoint.proceed();                      // ← 不调这行，目标方法永远不会执行
        logger.info("Method executed");
    }
}
ssh_ch6_ex1 · config/ProjectConfig.java
@Configuration
@ComponentScan(basePackages = "com.example.services")
@EnableAspectJAutoProxy                    // ← 开启 AOP，少了这个切面完全不生效
public class ProjectConfig {

    @Bean
    public LoggingAspect aspect() {        // ← 切面自己也必须是 bean
        return new LoggingAspect();
    }
}
三件缺一不可的事 ① 切面类标 @Aspect；② 切面类必须是 bean（这里用 @Bean 注册，也可以给它加 @Component）；③ 配置类标 @EnableAspectJAutoProxy。
@Aspect 本身不会把类变成 bean——这是新手最常犯的错。
依赖 第 6 章的工程比前几章多了一个 spring-aspects（仓库 7.0.1，书里 5.2.8.RELEASE）。它带来 AspectJ 的注解和切点表达式解析器。注意：用的只是 AspectJ 的“语法”，运行时仍然是 Spring 自己的代理机制。

切点表达式怎么读

拿到方法名、参数、返回值

ssh_ch6_ex2
@Around("execution(* com.example.services.*.*(..))")
public Object log(ProceedingJoinPoint joinPoint) throws Throwable {
    String methodName = joinPoint.getSignature().getName();
    Object[] arguments = joinPoint.getArgs();

    logger.info("Method " + methodName + " with parameters "
                + Arrays.asList(arguments) + " will execute");

    Object returnedByMethod = joinPoint.proceed();     // 目标方法的返回值

    logger.info("Method executed and returned " + returnedByMethod);

    return returnedByMethod;                           // ← 必须原样返回！
}
ex1 藏着一个 bug ssh_ch6_ex1 的切面方法返回 void。如果被拦截的方法本来有返回值，调用方会拿到 null——因为代理返回的是切面方法的返回值。所以除非你确定所有被拦截的方法都返回 void，@Around 的返回类型应该是 Object 并原样返回 proceed() 的结果。这就是 ex1 到 ex2 的关键变化。

切面可以改写调用

ssh_ch6_ex3演示切面的“权力”有多大
Comment comment = new Comment();
comment.setText("Some other text!");
Object[] newArguments = { comment };

Object returnedByMethod = joinPoint.proceed(newArguments);   // ← 换掉参数

logger.info("Method executed and returned " + returnedByMethod);

return "FAILED";                                             // ← 换掉返回值
能力越大越危险 切面可以：篡改参数、篡改返回值、吞掉异常、干脆不调 proceed()。这意味着一个写错的切面能让业务代码彻底失去意义，而业务代码里看不到任何线索。所以真实项目中的切面应该保持“横切且无副作用”：日志、监控、事务、鉴权、重试。ssh_ch6_ex3 是教学演示，不要模仿。

按注解匹配（推荐做法）

ssh_ch6_ex4
// 1. 定义一个自己的注解
@Retention(RetentionPolicy.RUNTIME)     // 必须是 RUNTIME，代理靠反射读它
@Target(ElementType.METHOD)
public @interface ToLog { }

// 2. 切点改成按注解匹配
@Around("@annotation(ToLog)")
public Object log(ProceedingJoinPoint joinPoint) throws Throwable { ... }

// 3. 在想拦截的方法上贴注解
@Service
public class CommentService {
    public void publishComment(Comment comment) { ... }    // 不拦截

    @ToLog
    public void deleteComment(Comment comment) { ... }     // 拦截

    public void editComment(Comment comment) { ... }       // 不拦截
}
这正是 @Transactional 的工作方式 Spring 的事务实现就是一个 @Around 切面，切点是 @annotation(Transactional)，前置逻辑开启事务，后置逻辑提交，捕获到异常则回滚。看懂了 ssh_ch6_ex4，第 13 章就没有秘密了。

@Before方法执行前否否
@After方法结束后（无论成败）否否

本章自测

为什么 @Aspect 类必须同时是 bean？

因为 Spring 只处理它管理的对象。@EnableAspectJAutoProxy 会在容器启动时遍历上下文里的所有 bean，找出标了 @Aspect 的，解析它们的切点，再给匹配的目标 bean 生成代理。一个不在上下文里的 @Aspect 类，Spring 根本看不到它。

为什么类内部的方法调用不会触发切面？

因为切面逻辑在代理对象上，而目标对象内部的 this.xxx() 是普通的 Java 方法调用，压根不经过代理（图 6-1 里那个最右边的框，它对代理一无所知）。绕过办法有几种：把方法拆到另一个 bean 里（最推荐）、注入自己的代理引用、或改用 AspectJ 编译期织入。第 13 章的 @Transactional 自调用失效是同一个原因。

Spring AOP 和 AspectJ 是一回事吗？

不是。Spring AOP 借用了 AspectJ 的注解和切点表达式语法，但运行机制完全不同：Spring AOP 是运行时动态代理，只能拦截 Spring 管理的 bean 的 public 方法；AspectJ 是编译期/类加载期字节码织入，能拦截任意类的任意方法（包括构造器、字段访问、private 方法）。绝大多数应用用 Spring AOP 足够。

Spring Boot 是怎么“猜”到我要用 Tomcat 的？

自动配置类里写满了条件判断，形如“如果 classpath 上存在 org.apache.catalina.startup.Tomcat 这个类，并且用户没有自己定义 ServletWebServerFactory bean，就注册一个 Tomcat 工厂”。因为 spring-boot-starter-webmvc 传递引入了 tomcat-embed-core，条件成立。想换 Jetty，就在依赖里排除 Tomcat 再加 Jetty starter——条件判断自然会走向另一条分支。

为什么控制器方法返回的字符串会变成一个页面？

因为 @Controller（不带 @ResponseBody）的返回值被当作视图名处理：DispatcherServlet 拿着这个名字去问视图解析器“哪个文件对应它”，找到后渲染成 HTML 写进响应。如果类上是 @RestController，返回值则直接被当成响应体写出去——这正是第 10 章的主题。

spring-boot-starter-web 和 spring-boot-starter-webmvc 能混用吗？

在 Boot 4 里两者都还能解析，但含义已经收敛：-webmvc 明确表示传统的 Servlet 阻塞式 Web 栈。仓库统一用 -webmvc，你自己新建工程时（比如从 start.spring.io 生成）也会拿到这个名字。书里的 -web 写法照抄到 Boot 4 工程里通常能跑，但不是现在的推荐写法。

本章自测

Model 里的数据能活多久？

只在这一次请求内。渲染完成，数据就没了。如果需要跨请求保留（比如登录后记住用户是谁），要用第 9 章的 session 作用域，或者 RedirectAttributes（跨一次重定向）。

@RequestParam 和 @PathVariable 怎么选？

看数据的角色：它是资源标识还是查询修饰。/products/42 里的 42 标识某个商品 → 路径变量；/products?category=book&page=2 里的两个值在筛选结果 → 查询参数。第 10 章做 REST 时这个区分更重要，因为它直接决定 API 设计的好坏。

为什么 @PostMapping 之后刷新会重复提交？

因为浏览器记住的“当前页面”是一次 POST 请求，刷新就是把这次 POST 再发一遍。标准解法是 POST-Redirect-GET：POST 处理完不直接渲染，而是返回 redirect: 让浏览器发起一次新的 GET。ssh_ch9_ex2 的 return "redirect:/main" 就是这个模式。

9.4 application 作用域：全应用共享

ssh_ch9_ex3 · services/LoginCountService.java

这段代码有并发 bug count++ 不是原子操作（读→加→写三步）。两个线程同时登录，可能都读到 17、都写回 18，丢掉一次计数。application 作用域的 bean 和单例 bean 面临完全相同的线程安全问题。

本章自测

为什么单例 Controller 能安全地持有 request 作用域的 bean？

因为注入的不是真实实例，而是作用域代理（图 9-2）。代理在每次方法调用时，从当前线程绑定的 RequestAttributes 里取出属于本次请求的真实实例再转发。这样单例的字段是固定的（指向代理），而实际干活的对象是每请求一份。

session 作用域的 bean 存在哪里？

存在 Servlet 的 HttpSession 里，Spring 只是替你管理键名和生命周期。这意味着：① 它受 server.servlet.session.timeout 控制；② 多实例部署时会出问题——用户下一次请求可能打到另一台机器，那台机器上没有这个 session。生产环境要么开启会话粘性，要么用 Spring Session 把会话放到 Redis。

什么时候该用 application 作用域，什么时候该用数据库？

判断标准是：这个数据丢了要紧吗、需要跨实例一致吗。缓存、限流计数器这类“丢了可重建、每实例一份也能接受”的，用 application 作用域没问题。像本章的“登录总次数”这种业务统计数据，应用一重启就归零、多实例还各算各的，正确做法是入库。

为什么推荐用 @RestControllerAdvice 而不是在控制器里 try/catch？

三个理由：① 控制器方法能保持精确的返回类型（ResponseEntity<PaymentDetails> 而不是 ResponseEntity<?>）；② 异常到响应的映射规则集中在一处，不会每个控制器写一份还各不相同；③ 业务代码只描述正常流程，可读性大幅提升。这是典型的横切关注点分离——和第 6 章 AOP 是同一个道理。

Jackson 是从哪里来的？我没加过这个依赖。

spring-boot-starter-webmvc 传递引入了 jackson-databind，Boot 的自动配置又注册了一个 MappingJackson2HttpMessageConverter。DispatcherServlet 发现返回值需要写成响应体、且客户端接受 application/json 时，就用这个转换器。整条链路你一行配置都没写——这就是第 7 章说的自动配置。

契约先行（OpenAPI）值得在真实项目里用吗？

取决于团队边界。如果 API 只给自己的前端用、且前后端同一个人写，代码优先 + springdoc 自动生成文档就够了。如果 API 要给别的团队/外部客户用，契约先行的价值很大：契约成为可评审、可版本化的交付物，双方能并行开发，还能自动生成各语言的客户端 SDK。

11.5 WebClient —— 响应式

ssh_ch11_ex4 · proxies/PaymentsProxy.java
@Component
public class PaymentsProxy {

    private final WebClient webClient;

    public PaymentsProxy(@Value("${payments.url:http://localhost:8080}") String paymentsUrl) {
        this.webClient = WebClient.create(paymentsUrl);
    }

    public Payment createPayment(String requestId, Payment payment) {
        return webClient.post()
                .uri("/payment")
                .header("requestId", requestId)
                .bodyValue(payment)
                .retrieve()
                .bodyToMono(Payment.class)
                .block();                    // ← 注意这里
    }
}
.block() 把响应式的好处全抵消了 WebClient 的价值在于非阻塞：发出请求后线程立刻去干别的，响应回来时再回调。而 .block() 让当前线程停在这里等——等于用响应式 API 做同步调用，白白背上了响应式的复杂度。

本章自测

为什么 Spring 官方说 RestTemplate 进入了“维护模式”？

因为它的 API 设计于 2009 年，方法重载多达几十个（getForObject/getForEntity/exchange/execute…），难以扩展也难记。Spring 5 先用 WebClient 提供了现代 API，但它是响应式的，逼着同步应用引入响应式依赖；Spring 6.1 于是推出 RestClient——WebClient 的流式 API + 同步语义。RestTemplate 不会被删除，但也不会有新特性了。

OpenFeign 相比 RestClient 的独特价值是什么？

它是声明式的：你只描述“调什么”，不写“怎么调”。在微服务体系里，它还能和 Spring Cloud 的服务发现（用服务名代替 URL）、负载均衡、熔断降级无缝集成。代价是多一个 Spring Cloud 依赖，以及一层抽象带来的调试成本。单体应用调几个外部 API，RestClient 更轻；微服务集群内部互调，Feign 更省事。

在 Spring MVC 应用里用 WebClient.block() 有什么问题？

你付出了响应式的全部成本（新的 API 心智、更难读的堆栈、额外依赖），却没拿到它唯一的好处（线程不被占用）。更糟的是，在某些线程配置下 block() 会直接抛 IllegalStateException（不允许在响应式线程里阻塞）。要同步就用 RestClient——它是专门为这个场景造的。

12.1 DataSource 是什么

建立一个数据库连接需要 TCP 握手 + 认证，通常要几十毫秒。如果每次查询都新建一个连接，性能会被这一步吃光。所以真实应用都用连接池——预先建好一批连接反复复用。DataSource 就是这个池子的抽象接口。

12.2 用 JdbcTemplate 读写数据

ssh_ch12_ex1 · repositories/PurchaseRepository.java
@Repository
public class PurchaseRepository {

    private final JdbcTemplate jdbc;

    public PurchaseRepository(JdbcTemplate jdbc) {     // Boot 自动配好了这个 bean
        this.jdbc = jdbc;
    }

    public void storePurchase(Purchase purchase) {
        String sql = "INSERT INTO purchase (`product`, `price`) VALUES (?, ?)";
        jdbc.update(sql, purchase.getProduct(), purchase.getPrice());
    }

    public List<Purchase> findAllPurchases() {
        String sql = "SELECT * FROM purchase";

        RowMapper<Purchase> purchaseRowMapper = (r, i) -> {   // 一行 ResultSet → 一个对象
            Purchase rowObject = new Purchase();
            rowObject.setId(r.getInt("id"));
            rowObject.setProduct(r.getString("product"));
            rowObject.setPrice(r.getBigDecimal("price"));
            return rowObject;
        };

        return jdbc.query(sql, purchaseRowMapper);
    }
}
两个核心方法 update(sql, args...) 执行 INSERT/UPDATE/DELETE，返回受影响行数；query(sql, rowMapper, args...) 执行 SELECT，用 RowMapper 把每一行变成对象。
? 占位符不是可选的——它是预编译参数，能杜绝 SQL 注入。永远不要用字符串拼接 SQL。
为什么用 BigDecimal 存价格 Purchase.price 声明成 BigDecimal 而不是 double。金额绝不能用浮点数——0.1 + 0.2 != 0.3。第 13、14 章的 Account.amount 同理。这是书里的一个好习惯，值得照抄。

为什么需要连接池？

建立数据库连接的成本（TCP 握手 + 认证 + 会话初始化）通常是几十毫秒，而一次简单查询可能只要 1 毫秒。不用池的话，绝大部分时间花在建连接上。连接池预先建好一批连接循环复用，把这个成本摊薄到接近零。Spring Boot 默认用 HikariCP，是目前性能最好的 Java 连接池。

JdbcTemplate 这个 bean 是谁创建的？

Boot 的 JdbcTemplateAutoConfiguration。它的条件是“classpath 上有 JdbcTemplate 类、上下文里有且仅有一个 DataSource bean、且用户没有自己定义 JdbcTemplate”。所以你只要引了 spring-boot-starter-jdbc 并且有数据源，就能直接注入它。

什么时候用 H2、什么时候用真实数据库？

H2 内存库适合：本地开发起步、快速演示、以及不涉及数据库方言的集成测试。但不要用 H2 测试依赖特定 SQL 方言的代码——H2 的 SQL 兼容层和真实 MySQL/PostgreSQL 有差异，测试通过了生产照样可能挂。更可靠的做法是用 Testcontainers 在测试时起一个真实的数据库容器。

坑一：默认只对运行时异常回滚

坑二：自调用不生效

@Service
public class TransferService {

    public void doTransfer(...) {

@Transactional 为什么必须标在 public 方法上？

因为 Spring AOP 通过代理实现事务，而代理（无论是 JDK 动态代理还是 CGLIB 子类）都只能拦截 public 方法——private 方法不可重写，protected/包级方法 CGLIB 虽能拦截但 Spring 默认不处理。标在 private 方法上不会报错，只是静悄悄地不生效，这比报错更危险。

为什么默认只对非受检异常回滚？

历史约定，继承自 EJB 的默认行为。背后的假设是：受检异常代表“预期内、调用方应该处理的业务情况”（比如“余额不足”），既然是预期内的，事务可能仍应提交；非受检异常代表“意料之外的故障”，应该回滚。这个假设在现代代码里往往不成立，所以很多团队直接约定所有 @Transactional 都写 rollbackFor = Exception.class。

事务和第 6 章的 AOP 是什么关系？

事务就是用 AOP 实现的。@EnableTransactionManagement（Boot 自动开启）会注册一个事务拦截器，它本质上是一个 @Around 通知：前置逻辑开事务、调用 proceed()、正常返回则提交、抛非受检异常则回滚。所以 AOP 的所有限制（自调用失效、只拦 public 方法、目标必须是 bean）在事务上原样成立。

为什么 AccountRepository 不需要 @Repository 注解？

因为 Spring Data 的 repository 扫描机制会自动找出所有继承了 Repository 体系的接口，为它们生成代理实现并注册成 bean。Boot 的自动配置默认扫描主类所在包及子包。加上 @Repository 也没坏处，但是多余的。

Spring Data JDBC 和 Spring Data JPA 该选哪个？

Spring Data JDBC：把对象直接映射成 SQL，没有会话、没有脏检查、没有延迟加载——你写的每个方法调用对应可预测的 SQL。适合领域模型简单、想掌控 SQL 的项目。
Spring Data JPA（Hibernate）：功能强得多（关联映射、二级缓存、乐观锁），但也带来复杂度（N+1 查询、LazyInitializationException、脏检查何时刷库）。团队熟悉 JPA、领域模型复杂时选它。
本书选 JDBC 是教学考虑，不是说 JPA 不好。

派生查询会不会在运行时才发现写错了？

不会。Spring Data 在应用启动时就解析所有 repository 方法名，解析不出来（比如实体上没有那个字段）直接启动失败并给出明确报错。这是"快速失败"的好设计——比上线后某个接口一调就崩强得多。

本章自测

为什么单元测试里完全不需要 Spring？

因为 Spring 的职责是“帮你把对象装配起来”。测试里对象由你手工装配（new TransferService(mock)），装配这件事就不需要框架了。好处非常实在：不启动上下文，一个测试从几秒变成几毫秒，几百个单元测试也能在一次保存后立刻跑完。

verify() 和 assertEquals() 什么时候各用哪个？

方法有返回值时，用 assertEquals 断言返回值；方法返回 void、效果体现在“调用了依赖”上时，用 verify 断言交互。transferMoney 返回 void，钱的变化是通过调用 repository.changeAmount() 实现的，所以只能用 verify。

mock 会不会让测试变得“测了个寂寞”？

这是个真实风险。如果 mock 的行为和真实实现对不上（比如你假设 findById 返回 Optional.of(...)，但真实实现在某些情况返回 empty），单元测试全绿而生产照崩。所以单元测试不能替代集成测试——第 16 章的 @SpringBootTest 用真实装配跑一遍，两者是互补关系，不是二选一。

本章自测

@MockBean 改名成 @MockitoBean 只是换个名字吗？

不只是。它的归属变了：从 Spring Boot 的测试模块（org.springframework.boot.test.mock.mockito）挪到了 Spring Framework 的测试核心（org.springframework.test.context.bean.override.mockito）。这意味着不用 Spring Boot 的项目也能用它，而且它属于一套更通用的“bean 覆盖”机制，同族还有 @MockitoSpyBean（部分 mock）和 @TestBean（用自定义实现替换）。

MockMvc 和真启动服务器（webEnvironment = RANDOM_PORT）有什么区别？

MockMvc 在同一个 JVM 里模拟请求，不经过网络栈，快很多，但也测不到真实的 HTTP 层行为（真实的连接、压缩、Servlet 容器配置）。@SpringBootTest(webEnvironment = RANDOM_PORT) 会真的启动 Tomcat，配合 TestRestTemplate/RestClient 发真实请求——更真实但更慢。绝大多数场景 MockMvc 就够了；只有验证真实 HTTP 行为（比如 HTTPS、超时、自定义 Servlet Filter）时才需要真服务器。

集成测试写多少合适？

测试金字塔的经验比例大致是 70% 单元 / 20% 集成 / 10% 端到端。集成测试贵在启动上下文，写太多整个构建会慢到没人愿意跑。把它们用在“装配和配置容易出错”的地方：REST 端点的契约、事务是否真回滚、自定义配置是否生效。纯业务分支留给单元测试。
